# ガラスメニューを閉じた後の引っかかり改善（2026-10-01）

## 調査結果

＋メニューを閉じた後の引っかかりを、実React部品と下部ガラス描画を使う合成画面で再現した。メニューの消去とフォーカス復帰は短時間で完了していたが、閉じた約0.2秒後に背景画像の再作成が始まり、ChromeのCPU 4倍条件で約170msのlong taskが発生していた。

閉じるCSSアニメーションだけを無効にしても引っかかりは残った。診断用に下部ガラス描画を止めると消えたため、原因はメニューのアニメーション時間ではなく、閉じた後の不要な背景画像化と判断した。通常のdismissは開閉で同じanimation-nameを使うため、検証したRadixでは直ちに取り外されていた。

描画元の監視は、Portalの追加・削除、Radixの`aria-hidden`、画像化対象外のFAB内の状態変更をすべて「背景の内容が変わった」と扱っていた。また、ページ最下部では実際のページ末尾より下まで画像が必要という判定になり、同じ範囲を繰り返し作り直す経路もあった。

## 改善

- Portalの監視を描画の休止・再開専用にし、開閉だけでは背景を更新扱いにしない。
- 画像化の対象外にしているFABなどの変更、アクセシビリティ用の非表示属性、短い押下表示を更新理由から外す。「…」メニューのトリガーには専用の印を付け、開閉状態だけの変更を判別する。
- 実際の本文・選択・CSS・入力・画像読み込み・大きさの変更は引き続き追跡する。メニュー表示中の変更を保持し、最後の画面が閉じて操作が落ち着いてからまとめて描画する。
- 新UIの隠しマーカーは背景全体のCSSを切り替えるため、画像化対象外でも変更検知から外さない。
- キャッシュの有効範囲を実際のページの上下端で制限し、存在しない範囲のために再作成しない。
- 既存v6のモーダル中の休止処理を保守用ソース・ビルド手順にも反映し、固定Git版からvendor v7を再生成した。

メニューの見た目、削除確認、コピー時のuser activation、Radixのフォーカス・スクロール引継ぎは維持。ガラスの光学シェーダー7個は改行差を正規化して一致。384px・最大1.5倍の画像上限、背景座標、下部タブの操作も維持。描画キャッシュの最適化は共通描画部分に適用するが、管理者の端末別新UI設定や通常版の表示範囲は変えない。DB/GAS/PC定期処理の変更なし。

## 修正前後の計測

同じ30行の合成画面、390×844px、スクロール750px。メニューを650ms表示してから外側へのブラウザタッチまたはEscで閉じ、その後1.3秒のフレームを記録した。各条件3回の中央値。ChromeはCPU 4倍、WebKitは通常CPUで、計測中は別のビルドやUI試験を並走させていない。

| 条件 | 最大フレーム間隔・修正前 → 後 | long task合計・修正前 → 後 | 背景再作成 |
| --- | ---: | ---: | ---: |
| Chrome・外側タッチ | 169.6 → 18.7ms | 168 → 0ms | 1 → 0回 |
| Chrome・Esc | 173.6 → 18.7ms | 169 → 0ms | 1 → 0回 |
| WebKit・外側タッチ | 49 → 30ms | API非対応 | 1 → 0回 |
| WebKit・Esc | 48 → 30ms | API非対応 | 1 → 0回 |

メニュー自体が消えるまでの時間はChrome外側タッチ35.8→37.3ms、WebKit24→23msで同程度。改善したのは、その直後に入っていた長い処理と画面の引っかかり。実機で同じ数値・短縮率になるという意味ではない。
