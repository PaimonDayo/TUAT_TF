# 個人Googleアカウントのログイン許可リスト

## 開始（2026-10-11 / Codex）

所有者依頼: 管理画面から指定した人だけ個人Googleアカウントで利用できるようにする。対象メールは未定で、実メールをソースへ入れない。

コード確認で、Googleの大学ドメイン指定・callbackの大学ドメイン判定・Before User Createdフックが大学限定であることを確認。実Googleアカウントによる再現は未実施。

受入条件:
- 部員・ロール管理権限で、正規化したメールの追加・一覧・削除ができる。一般部員・未ログイン・プレビューから変更できない。
- 大学アカウントは従来どおり。個人Googleアカウントは完全一致する許可メールのみ。追加しても管理ロールは付けない。
- 新規登録フック・callback・既存セッションのデータAPIで同じDB判定を使い、削除後も既存セッションで利用を継続させない。
- 取得失敗を空リストにしない。重要な変更は返却件数を確認。応答不明時は再読込で確認するまで再送しない。
- 既存データ・ロール・通常ログイン・cookieを保全。一時的な接続失敗でcookieを削除しない。

最新origin/masterをfetchし、既存変更を保全するため専用worktree `.worktrees/login-allowlist` で実装する。本番DBへの適用前に履歴・snapshot・dryRunが必要。

## 実装・本番DB反映（2026-10-11 / Codex）

所有者の「もし大丈夫そうであれば本番実装して」により、この許可リスト機能の本番反映を進める。他の公開保留中の変更は含めない。

管理画面の「ログイン許可リスト」で、部員・ロール管理権限を持つ人がGoogleメールを追加・一覧・取り消しできる。大学メールは従来どおり利用でき、外部メールの追加だけでは管理権限を付与しない。対象メールが未定のため、本番リストは空で開始する。

PC DBを正本とし、既存の5分ごとのmirrorでクラウドAuthへ配る。PC停止中の予備側からリストは変更できない。他表の既存書戻しは維持する。反映は同期状況により数分かかる。取り消しは以後のデータ操作・画像URLの新規発行を拒否するが、発行済み画像URLは既存の有効期限まで残る。

新規登録フック、callback、個人メールのproxy、PostgRESTのpre-requestと既存RLS表・Storageのrestrictive policyで同じ判定を使う。新しいRLS表を将来追加する場合も `require_login_access` を付けること。取得失敗は空リスト扱いにせず、保存結果不明時は再取得で照合するまで再送しない。一時的な認証DBの障害では有効cookieを消さない。
