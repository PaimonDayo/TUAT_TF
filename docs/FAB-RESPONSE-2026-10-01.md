# ＋メニューの白い重なりとFABの応答改善（2026-10-01）

対象は現行アプリ。管理者の端末別「新UI版」の＋メニューと共通操作メニューを修正し、FABのフォーム表示と背後の下部ガラス描画を軽量化した。

## 原因と変更

- メニューは白いグラデーションと半透明の下地が重なり、上部ほど白くなっていた。均一な半透明面へ変更し、ぼかしを26pxから18pxへ調整。backdrop-filterを持つ面自体の拡大縮小をやめ、位置・寸法を固定した120msのフェードにした。画面上部全体が白く覆われる現象はWindowsの検証環境では再現せず、報告端末での確認は残る。
- 項目選択後、130msのメニュー終了アニメーションを待ってからフォームコードを読み込んでいた。選択時だけ終了アニメーションを省き、Radixのアンマウント・スクロールロック解除・フォーカス復帰が済んでからフォームへ渡す。外側やEscで閉じる場合は90ms。任意の固定タイマーによるダイアログ重複は作らない。
- フォームコードはFABへのポインター・フォーカス、選択肢への操作意図で先読みする。初期表示で全フォームを取得せず、先読みではフォームをマウントせず、DB取得・保存も開始しない。
- コードを先読みしてもNext App Routerのdynamic/Suspenseで約300msの待ち表示が残ったため、読み込み済みなら実コンポーネントを直接表示する `withIntentPreload` を追加。準備前のオープンは既存のdynamicとスケルトンを使用する。表示するコンポーネントはマウントごとに固定し、先読み完了や親の再描画で入力中のフォームを置き換えない。失敗した先読みは再試行可能。
- 素早い再オープンで、選んだ入力欄から日付欄へ遅れて自動フォーカスが移る競合も修正。すでにフォーム内を操作している場合は自動フォーカスを省き、DOMが外れたら予約フレームを取り消す。
- メニュー・フォーム・確認画面の裏でもガラス背景を画像化していた。vendor v6はdialog/alertdialog/通常版作成メニューの存在中、画像化と毎フレームの座標読取・描画を休止する。画像を保持し、最後のダイアログが外れた後に更新を再開する。body直下のPortal監視を追加し、モバイル終了時には監視も解除する。

固定版シェーダー・画像化プリミティブは改行を正規化した比較で同一。下部384px・倍率1.5の上限を維持。下部タブの操作・表示、管理者opt-in、通常版の外見、DB・GAS・PC定期処理は変更しない。

## 検証

- 既存551テスト、変更TSX/TSのeslint、Next 16.3.6の隔離合成本番buildとTypeScript検査に成功。主作業ディレクトリの依存関係・環境変数・本番データを使用/変更せず実行。
- 実ReactコンポーネントとApp Router用dynamicを使用したローカル合成UIでChrome/WebKit、320/390/1440px、新旧UIの12条件を検証。メニュー全項目、キーボード移動、Esc、外側、フォーカス復帰、練習記録入力、未投稿確認、保存失敗時の入力保持、破棄、閉じた後の描画再開が成功。
- 12条件でメニュー開閉前後の見出し・ページスクロール位置差0px。モバイルではメニュー・フォーム表示中の背景画像再作成0回。旧版ではそれぞれ1回だった。
- Chrome/WebKitの390pxでつぶやき・ストーリー・大会結果・フォルダ・記事・サブフォルダ・スレッド・お知らせ・予定の9経路も実フォームを開いて閉じることを確認。コピーの直接user activation、削除前確認と削除失敗時の確認画面保持も成功。
- 390→1440→390pxで追加Portal監視数は1→0→1。軽減モーション・強制色の代替表示、一般部員の通常版への切替も成功。
- フォームコードを1秒遅延した未準備時の表示、読み込み前に閉じて再度開く操作、入力直後の親state更新、未投稿確認からref経由で保存して失敗した場合の入力保持もChrome/WebKitで成功。
- ブラウザ入力のタッチ操作とスクリーンショットを確認。Windows WebKitは操作・配置の検証用。iPhone/Android実機の質感とキーボードは未確認。

検証スクリプト・スクリーンショット・合成データは `.contingency/fab-response-ui`、`verify-fab-response.cjs`、`verify-fab-extra.cjs`、`benchmark-fab-response.cjs` と各結果JSONにローカル保持する。

### 反応時間の比較

同じ合成30行、390×844px、実ブラウザのタッチ入力、フォームchunk応答を150ms遅延、メニューを650ms表示してから選択する条件で各3回測定。ChromeはCPU 4倍スロットル、WebKitは通常CPU。クリックイベント到着から実入力欄がDOMに表示された最初のフレームまでの中央値で、Playwrightの操作待ち時間は含めない。

| 指標 | 修正前 | 修正後 |
| --- | ---: | ---: |
| Chrome 入力欄表示 | 604.6ms | 230.9ms |
| WebKit 入力欄表示 | 381ms | 69ms |
| Chrome メニュー表示中のlong task合計 | 198ms | 0ms |
| Chrome フォーム表示時のlong task合計 | 321ms | 179ms |
| メニュー／フォーム中の背景画像化 | 各1回 | 各0回 |

初回DOMのメニュー出現自体はChrome約110msで同程度。改善は表示中の引っ掛かり、アニメーション完了、フォーム入力欄の待ちにある。WebKitはlong task API非対応のためlong task値を比較しない。実端末・実通信・本番データで同じ短縮率になるとは扱わない。
