# OBOG戦の構造・UI調査（2026-10-11）

## 調査開始

- 依頼: 突貫実装と後付け改善で、追加・複数エントリー・削除に弱く、画面と操作が他機能から乖離した原因を調べる。

## 結論

出発点が「フォームの回答を人ごとに一覧にする機能」で、その登録行へ競技運営を積み足している。人・参加登録・種目ごとの出場・組/レーン・結果の境界が弱く、操作ごとに整合を補う必要がある。画面にもその分割が露出し、参加者管理・当日登録・組分け・記録・本人照合を利用者が行き来して整合させる構成になっている。

これはコードからの設計上の評価であり、作成当時の担当者の意図・工期・判断過程までは断定しない。共通UI部品、競合検出、監査、原子的保存は既に整備されている。問題は、それらを足しても通常操作の単位と入口が十分に整理されていないことにある。

## 1. 人の登録と出場のモデル

### 1-1. 「出場1件」が独立した登録データになっていない（高）

- `ob_meet_entries` は氏名・学年・本人アカウント・出場種目配列・資格記録を持つ人単位の行。初期定義は `(meet_key, submitted_name)` を一意とし、本人IDにも大会内の一意制約を持つ。
- 10/11の複数出場対応は、`events` に同じ種目名を2回入れ、運営JSONの1件目を登録UUID、2件目を `UUID:2` にする方式。出場の有効性は種目名の出現回数から計算する。
- 件数を2→1へ減らす操作は末尾の種目名を削除するため、登録取消の対象は必ず2件目。1件目の登録だけを取り消して2件目を維持する表現はない。記録画面で1件目だけDNSにする操作は別に可能なので、「個別DNSができない」という指摘ではない。
- 最大2件はUI、TypeScript検証、DB trigger/RPCに埋め込まれている。3件以上、出場ごとに異なる資格記録、新しい出場IDによる再登録へは自然に拡張できない。資格記録は種目名をキーにするため2出場で共有する。

根拠: `src/lib/ob-entries.ts:1,23`、`src/components/features/ObEntryEditor.tsx:122,132`、`src/lib/ob-entry-edit.ts:32`、`supabase/migrations/20261011060000_ob_double_entry.sql:1,9,20`。

「2件に対応していない」は既に過去の問題。現在の問題は、対応後も独立した出場の登録/取消として扱えないこと。上限を増やすだけでは解消しない。

### 1-2. 氏名を識別子に近い扱いにしている（高）

- 同じ正規化氏名があれば、学年や本人IDが異なってもゲスト新規登録を拒否する。参加者管理の「新規部員」候補も本人IDまたは正規化氏名の一致で除外する。
- 実際に同姓同名の別人が来ると、追加経路が閉じる。同じ本人の二重登録を防ぐ目的と、別人を区別する目的が混ざっている。
- フォーム回答とアプリアカウントが別で、未照合の現役・ゲスト・OB/OGを扱うこと自体は必要。氏名一致を自動の本人認証にしない現在の方針は維持すべき。

根拠: `supabase/migrations/20260924030000_ob_meet_entries.sql:12`、`supabase/migrations/20261003010000_ob_program_access_registration.sql:17`、`src/components/features/ObMeetParticipants.tsx:50`。

### 1-3. 大会・種目・時刻・権限が2026年の1大会に固定（中）

大会UUID、`ob-2026`、`OB戦2026`ロール名、タイムテーブル、種目リスト、懇親会の店・金額が定数やSQLに入っている。種目判定にも `男子/女子` の文字列先頭と正規表現を使う。通常の大会プログラムとは同じURL内の特別分岐になっている。

次年度・種目変更・時刻変更で表示、補助担当の競合判定、入力検証を複数箇所で直す必要がある。4×300mリレーはタイムテーブルに「当日エントリー」と出るが、種目リスト/RPCの対象には入っていない。今回の登録・組分け・記録と同じ経路では扱えない。

根拠: `src/lib/ob-meet.ts:7,22,38,46`、`src/lib/ob-entry-edit.ts:3`、`src/app/(app)/competitions/[id]/program/page.tsx:42`、`supabase/migrations/20261011060000_ob_double_entry.sql:237`。同名ロールへの依存は現行権限ガイドにも明記されている。調査では権限を変更していない。

## 2. 追加・取消・削除・復帰の操作

### 2-1. 同じ追加でも通常登録と当日登録で動作が違う（高）

| 利用者の目的 | 現在の入口・動作 | 残る負担 |
| --- | --- | --- |
| 新しい人を登録 | 参加者管理→参加者を登録→部員選択/名前入力 | 懇親会・本人・種目・資格記録を同じフォームで扱う |
| 登録済みの人へ種目を追加 | 参加者詳細→…→エントリー編集 | 種目の記録画面から始めた操作とは別経路 |
| 当日に種目へ出場を追加 | 組分け/記録の内部→当日エントリー | 短距離は組未定、フィールドは順番未定。配置は別操作 |
| 取り消した出場を復帰 | 登録編集で再登録→記録でDNS解除→配置 | 当日追加のRPCは既存DNS/試技がある出場IDの再利用を拒否する |

当日追加は「記録済みの組全体には追加不可」という過去の制約を解消済み。ただし確定済み種目は引き続き追加不可で、確定解除が必要。これは結果保護の制約であり、無条件に撤去する問題ではない。

競技一覧は登録または運営データが存在する種目だけを並べる。全体に登録が1種目でもあると、一覧の「出場者を追加」は消え、組分け/記録の内部へ入る必要がある。まだ誰も登録していない種目へ追加するときに、入口を探しにくい。

根拠: `src/components/features/ObDayRegistration.tsx:45,71,76`、`src/components/features/ObOperations.tsx:24,49`、`supabase/migrations/20261011060000_ob_double_entry.sql:254,267`、`src/app/(app)/ob-entries/operations-actions.ts:54,60`。

### 2-2. 削除は実装済みだが、運営を始めると使えなくなる（高）

現在は参加者詳細の共通ActionMenuから登録全体を削除できる。ただしDBは、補助担当がある場合、または運営JSONの `participants` に登録ID/2件目IDが存在する場合に拒否する。後者は実際の試技・組番号の有無を見ていない。未配置・未記録でも運営データに入っていれば対象になる。

種目登録を取り消しても、運営側の出場行はDNSとして残るため、取消のあとに物理削除が可能になるわけではない。案内は「削除せず、エントリー編集で種目を取り消してください」で、名簿から除く・記録は保管するという作業は一つの操作として用意されていない。

履歴・結果・懇親会回答を守る制約には理由がある。問題は「削除」の適用範囲が狭いこと、参加取消や通常一覧からの除外と記録保管を明示した代替操作が不足していること。依存データを一括削除する解決は不適切。

根拠: `src/components/features/ObMeetParticipants.tsx:135`、`src/app/(app)/ob-entries/actions.ts:253`、`supabase/migrations/20261011060000_ob_double_entry.sql:364`。

### 2-3. 登録・大会欠席・DNS・復帰を横断して理解する必要がある（高）

最新仕様は大会欠席、種目登録取消、参加情報なし、明示DNSを競技上はすべてDNSへ揃え、配置を解除し、試技を保持する。これは10/11に修正済みで、今回の調査でも純粋関数の実行で確認した。

一方、元の状態は人の `absent`、種目配列、運営JSONの `status` に分かれる。大会欠席を取り消す/種目を再登録するだけでは保存されたDNSは戻らず、記録画面で明示的に戻す必要がある。配置も自動復帰しない。最新の所有者指示である記録保持・手動復帰は尊重しつつ、現在の状態と次に必要な操作を同じ対象の画面で案内する必要がある。

根拠: `src/lib/ob-operations.ts:28,38`、`src/components/features/ObMeetParticipants.tsx:172`、`supabase/migrations/20261011100000_ob_unified_dns.sql:2,21`。

## 3. UIの乖離と具体的な不整合

### 3-1. 画面名と作業の入口が一致していない（高）

- 上部は独自の横スクロールLinkタブで「競技・記録 / 組分け / シフト表 / 自分の登録 / 参加者管理」。参加者管理にはさらに共通SegmentedControlによる「エントリー / 懇親会」、独自の絞り込みボタン列がある。
- 「組分け」タブは `ObPublicProgram` を表示する閲覧用。組分けの編集入口は「競技・記録」内の同名ボタンにある。閲覧と編集の違いをタブ名から判別できない。
- 自分の登録タブにも全体プログラムを再表示する。タイムテーブルは登録フォームの折りたたみにもあり、同じ情報の入口が複数ある。
- 互換URLも `view=program` が `mine` に変換されるなど、名前と到達画面が一致しない。古いリンクを保つ必要はあるが、現在の画面構成が読み取りにくい。

根拠: `src/components/features/ObMeetWorkspace.tsx:24`、`src/app/(app)/competitions/[id]/program/page.tsx:69`、`src/components/features/ObMeetParticipants.tsx:68`、`src/components/features/ObEntryEditor.tsx:95`、`src/lib/ob-meet-navigation.ts:7`。

### 3-2. 保存・終了・選択の作法が混在（中）

登録と組分けは保存ボタン、記録は入力終了後600msの自動保存と失敗時の再試行ボタン。氏名/学年と本人照合を参加者詳細の全画面フォーム内で直接操作する一方、編集はその詳細の「…」から別の全画面フォームへ遷移する。種目はチェック、出場数はSelect、組の移動はチェック＋固定フッター、組内はドラッグ、試技順は別ボードという複数の操作が並ぶ。

競技固有の操作や記録の連続入力には理由があるため、すべてを一つの部品へ機械的に揃えるべきではない。しかし保存済み/未保存/復旧中の見え方、詳細→編集の入口、選択と入力の役割は共通の作法へ揃える余地がある。

FormModal、Button、Select、ActionMenu、ConfirmDialog、FormDraftGuard、競合確認は既に使っている。「共通部品をまったく使っていない」「全フォームが独自シート」という評価は現行コードと異なる。ガラパゴス化の中心は部品の有無より情報の階層と操作の組合せにある。配色やガラスの実表示は今回未確認。

根拠: `src/components/features/ObEventOperationsEditor.tsx:55`、`src/components/features/ObHeatEditor.tsx:42`、`src/components/features/ObMeetParticipants.tsx:131`、`src/components/features/MeetHeatBoard.tsx`、`src/components/features/MeetFieldOrderBoard.tsx`。

### 3-3. 最新処理に追従していない文言・人数表示（明確な現行不整合）

1. 大会欠席の確認文は「登録種目・組番号・記録は保持します」。最新処理は組/番号を解除する。利用者が保存後の結果を誤解する。
2. 欠席取消の説明は「出場予定に戻ります」。保存済みDNSが維持されるため、競技上の出場復帰まで完了したと読める説明は不十分。
3. 同じ人の2出場を `participating.length` や `rows.length` で数え「人」と表示する。純粋関数で実人数1人・出場行2件を確認。参加者管理の人単位の人数と競技/公開プログラムの人数が一致しない。
4. 競技一覧は `status !== entered` を「DNS」と集計するため、DNF/DQもDNS人数に含める。最新のDNS統一は大会欠席/取消等の話であり、DNF/DQとは別。記録人数もDNSの保存済み試技を含めて数える。
5. 「本人照合」「紐付け」「本人未確認」など登録元の仕組みを説明する言葉が前面に出る。同じ作業を異なる語で表しており、通常の参加者追加とアカウント確認の違いが読み取りにくい。

根拠: `src/components/features/ObMeetParticipants.tsx:111,122,172,181`、`src/components/features/ObOperations.tsx:41`、`src/components/features/ObPublicProgram.tsx:41,56`。1・3・4はコードから確定できる。2・5の理解しにくさは使い勝手の評価で、実利用者での確認は未実施。

## 4. 後付け変更が高コストになる理由

- 組・レーン・試技順・試技・出場状態・確定を種目ごとの1個のJSONに保存し、revisionも種目全体で管理する。人単位の編集も種目全体の保存と検証になる。同一種目を複数人が編集する場合の競合範囲が広い。現在は差分照合/競合解決で保護しており、無条件の上書きになっているという指摘ではない。
- 混合組/全体試技順は男女別データを表示時に投影し、保存時に分解する。配置と記録が同じJSONにあるため、組分け変更にも結果保持と男女の整合確認が必要。
- 補助担当は旧profile_id単位の `ob_meet_duties` とentry_id単位の `ob_entry_duties` を併用し、読取り時に結合する。未照合の人を扱えるよう改善した結果だが、本人照合・担当解除・削除で両方を考慮する必要が残る。
- 出場数の表現がTypeScriptとSQL、組分け、結果、本人表示、公開プログラム、出力にまたがるため、複数出場の変更が広範囲へ波及する。10/11の修正記録もこの対応範囲を示している。

根拠: `supabase/migrations/20261002010000_ob_event_operations.sql:2`、`src/components/features/useObOperationDraft.ts:18`、`src/components/features/useObFamilyDraft.ts`、`src/lib/ob-mixed-operations.ts`、`src/lib/ob-duty.ts`、`docs/OB-DOUBLE-ENTRY-2026-10-11.md`。

## 6. 改善の優先順位

1. **状態と操作を整理する。** 人の登録削除、出場取消、DNS、大会欠席、出場復帰を区別し、結果を保持したまま誰を通常一覧に残すか定義する。最新のDNS配置解除・履歴保持・手動復帰は維持。各対象の詳細から必要な操作と影響対象を確認できるようにする。
2. **入口・文言・集計を揃える。** 組分けの閲覧/編集を同じ対象から開けるようにし、未登録種目への追加を常に探せる入口を用意する。「人」と「出場件数」、DNS/DNF/DQを区別。欠席確認文を実処理に合わせる。新しい警告や別設定を増やす必要はない。
3. **出場を独立したIDと状態で扱う。** 人の大会参加に、種目ごとの出場登録を複数紐付け、配置/試技は出場へ紐付ける。資格記録の共有/個別は利用目的から決める。氏名は表示と候補検索へ戻し、別人の同姓同名を表現できるようにする。
4. **既存大会のデータと共通UIへ寄せる。** 必要な大会条件、種目、時刻、運営権限を大会に紐付ける。補助担当は人の大会参加にまとめ、懇親会は競技出場の増減から独立させる。今回の弱点を解消する範囲で行い、汎用大会プラットフォームの新設や一括作り直しへ広げない。

改善の受入試験は、未登録の種目への当日追加→配置→記録、同じ人の複数出場→指定した片方だけ取消/復帰、同姓同名の別人登録、未記録者の削除、記録者の取消と記録保持、大会欠席→枠の再利用→未配置から復帰、担当解除/交代、競合/結果不明からの復旧を一連で行う。人数制限や初期値、入口の名前そのものが妥当かも確認する。
