## 1. 🔴 権限関数が未ログインでも true を返す

**症状**: 認証なしの呼び出しで `can_create_notice()` が **true** を返す。
`notices` の insert / update / delete ポリシーはこの関数だけを条件にしており、対象ロールが `public`（anonを含む）。
匿名ロールで insert を試すと、**権限では弾かれず**、必須列の NOT NULL 制約でだけ止まった＝判定は通過している。
お知らせの作成は全部員への通知を起動するため、影響は通知にも及ぶ。

**原因**: 権限関数が「全員に自動適用されるロール（`roles.is_everyone`）」で本人確認を短絡している。

```sql
SELECT EXISTS (
  SELECT 1 FROM roles r
  WHERE r.can_create_notice
    AND (r.is_everyone OR EXISTS (           -- ここで auth.uid() の確認を飛ばす
      SELECT 1 FROM profile_roles pr
      WHERE pr.role_id = r.id AND pr.profile_id = auth.uid()
    ))
);
```

`auth.uid()` が NULL でも、`is_everyone` のロールにフラグが立っていれば true になる。
現在ロール「全員」には `can_create_notice=true` が設定されている（2026-07-15「ロールに全員自動適用」で入った仕組み）。

**同じ短絡を持つ関数（実測）**:

| 関数 | 短絡 | 現在 |
|---|---|---|
| `can_create_notice` | あり | **開いている** |
| `can_create_menu` | あり | 閉（全員ロールにフラグ未設定） |
| `can_create_schedule` | あり | 閉（同上） |
| `can_manage_members` | あり | 閉（同上） |
| `can_manage_system` | あり | 閉（同上） |
| `is_admin` / `is_member` / `is_staff` | なし | 安全 |

**つまり、管理画面で「全員」ロールに権限チェックを1つ足すと、その機能が匿名へ開く。**

**直し方**: 5つの関数の先頭に本人確認を足す。権限の設定は一切変えずに塞げる。

```sql
CREATE OR REPLACE FUNCTION public.can_create_notice() RETURNS boolean AS $fn$
  SELECT auth.uid() IS NOT NULL AND EXISTS ( ... 既存のまま ... );
$fn$ LANGUAGE sql STABLE SECURITY DEFINER;
```

**即応（migration を待てない場合）**: 管理画面でロール「全員」から「お知らせを作成」を外す。
ただし一般部員がお知らせを作れなくなるため、仕様としてそれでよいかはオーナー判断。

**確認方法**:

```sql
BEGIN; SET LOCAL ROLE anon;
SELECT public.can_create_notice();  -- false になること
ROLLBACK;
```

## 2. 🔴 書き込みポリシーの大半が `TO public`

**実測**: `public` スキーマの insert / update / delete ポリシー **95本中71本**が `TO public`（anonを含む）。

2026-06-24 の修正（SELECT を `TO authenticated` ＋ `REVOKE anon`）は**読み取りだけ**が対象で、
書き込み側は手つかずのまま残っていた。項目1の穴はこの上に乗っている。

**直し方**: 書き込みポリシーを `TO authenticated` へ寄せる。項目1を直せば実害は消えるが、
同じ穴を二度作らないための構造的な防御として入れる価値がある（関数とRLSの二重）。

## 3. 🔴 Web Push が 2026-09-17 から不通

**症状**（実測）:

```
vault.decrypted_secrets : 0件（空）
VAPID鍵                 : 送信関数の環境変数になし、.contingency/backend/push.env も存在しない
DBログの警告            : "push_webhook_secret is not configured; push delivery skipped" 7.5時間で34回
直近24時間の通知        : 5件 → すべて未配信
購読中                  : 11台 / 9人
```

**原因**: 9/17 の新PCへの移設で、Vault の中身と VAPID 秘密鍵が移らなかった。
2026-09-10 に「DBを移しても黙って止まらないように」と送信先URLを Vault へ移した経緯があるが、
**Vault 自体が移行対象に入っていなかった**ため、結局また無言で停止した。

**直し方**: `ops/laptop/generate-push-keys.mjs` で鍵を再生成 → 送信関数へ設定 → Vault に
`push_webhook_secret` と送信先URLを登録 → Vercel の `NEXT_PUBLIC_VAPID_PUBLIC_KEY` を差し替え。
端末側は公開鍵が変われば `PushSubscriptionSync` が自動で購読し直すので、部員の操作は不要。

**あわせて直すべき根本**: バックアップに Vault・鍵・cron 設定が含まれていない。
いまのバックアップから復旧しても Push は復活しない（今回それが起きた）。
`ops/laptop/backup-backend.mjs` の対象と `SERVER-HANDOFF.md` の引き継ぎ手順に追加する。

## 5. 🟠 R2のバックアップに保持ルールがない

**実測**: R2 全体 2.18GB のうち **2.17GB がDBバックアップ**。部員の画像は 12MB だけ。
15分ごとに保存して**一度も削除していない**ため、1日 240MB 増え続ける。

`backup-backend.mjs` の `KEEP_LOCAL_BACKUPS=24` は**ローカル控えだけ**で、R2 側に保持ルールがない。

**影響**: 画像アップロードには `R2_MAX_STORAGE_BYTES=8GB` のガードがあるため、
このままだと**約3週間で部員が画像を上げられなくなる**。

**直し方**: 直近24時間は15分ごと、それ以前は1日1つを30日分、それより古いものは削除。
削除は取り返しがつかないので、オーナーの承認を得てから実行する。

**補足**: R2 へ送れていないローカル控えが8件ある（9/20 20時前後＝再起動の前後）。
R2側のバックアップにその時間帯の穴がある。

## 7. 🟡 死活確認がDB最大の負荷

**実測**（pg_stat_statements・8.5時間ぶん）:

| 実行者 | 回数 | 総DB時間 | 中身 |
|---|---|---|---|
| anon | **5,851回** | **94.8秒** | スキーマ全体の調査（毎回227,058行を読む） |
| authenticated | 203回 | 14.8秒 | 練習記録の取得（アプリで最も重いクエリ） |

`postgrest --ready` の死活確認が **5秒間隔**で走り、毎回スキーマ全体を調べ直している。
**アプリのどのクエリより6.4倍重い。** 11コンテナ中8つが5秒間隔。

`supabase-db` がアイドルで 13.6% CPU を使っている原因でもあり、電力にも効く。

**直し方**: 死活確認の間隔を 30 秒へ。**コンテナの作り直しが必要でAPIが一時的に止まる**ため、
部員が使っていない時間に実施する。compose は必ず4ファイルを揃えること（2026-09-10 の12分障害の教訓）。

## 8. 🟡 練習記録の取得の72%が無駄

**実測**（タイムライン30件の実バイト数）:

| 中身 | サイズ |
|---|---|
| 著者情報（`record_fields` 込み） | 41.3 KB |
| `record_fields_snapshot` | 34.4 KB |
| 実際の記録（距離・感想・結果・追加項目） | 約10 KB |
| **合計** | **109.1 KB** |

**109KB中78KB（72%）が「記録フォームの項目定義」の繰り返し。**
不要な繰り返しを外すと **109.1 KB → 30.7 KB**（実測）。練習記録は全転送量の **47%** を占める。

`queries/internal.ts` のコメントに当時の担当者自身が残している:

```
// Tweets never render practice-record fields. Avoid repeating every author's
// form configuration in each tweet; records still use AUTHOR_SELECT above.
```

2026-09-06 の転送量削減で、つぶやきと名簿からは外したが**練習記録は手つかず**だった。

**直し方**: 単に列を消すのではない。記録カードは `record_fields_version` があれば
`record_fields_snapshot` を、なければ著者の `record_fields` を使って項目名を出している。
**「毎行に付ける」のをやめて「1回だけ取る」形**に変える必要がある。

## 9. 🟡 毎レンダリングで権限とユーザーを取り直している

**実測**（86時間のリクエスト数）:

| 取得先 | 回数 | 1時間あたり | 性質 |
|---|---|---|---|
| `/auth/v1/user` | 38,266回 | 439回 | 画面を作るたびの本人確認 |
| `/rest/v1/roles` | 4,737回 | 55回 | **全員同じ・ほぼ不変** |
| `/rest/v1/profile_roles` | 4,736回 | 55回 | ほぼ不変 |

`fetchRolesByProfileIds()` が `getCurrentProfile()` から毎回呼ばれ、2テーブルを引いている。
ロール一覧は全員にとって同じ内容で、月に1回変わるかどうか。

**直し方**: `roles` はサーバー側で共有キャッシュ（数時間でよい）。
`auth.uid()` だけで足りる箇所は `getCurrentUserId()`（cookieを読むだけ・DB不要、2026-09-13に追加済み）へ置き換える。

**注意**: `cacheComponents` と `experimental.staleTimes` は iOS PWA のフリーズ原因で**再導入禁止**。
ここで言う共有キャッシュは「データを覚えておく」ことで、画面そのもののキャッシュとは別物。混同しないこと。

## 10. 🟢 無料プランへ戻すための条件（調査済み）

### Vercel Hobby

公式の制限（2026-09-21 確認）:

| | Hobby | Pro |
|---|---|---|
| cronの本数 | 100本 | 100本 |
| 最短の間隔 | **1日1回** | 1分 |
| 時刻の正確さ | ±59分 | 分単位 |

毎時の cron はデプロイ自体が失敗する。大会プログラムの取得は 2026-09-21 に日次へ変更済み。
**残る毎時は予定・メニュー取込の1本**で、クラウドDBへ戻すときに pg_cron へ移す。

使用量の実測（`vercel usage`・東京リージョンの単価で逆算した概算）:

| | いま（PC中継） | PC中継をやめた場合 | Hobby無料枠 |

| Active CPU | 約12〜15時間/月 | 約6.4〜7.6時間/月 | **4時間** |
| Fast Origin Transfer | 約25〜40GB/月 | 約12〜15GB/月 | 10GB前後 |
| 関数の呼び出し | 約70〜110万回/月 | 約35〜45万回/月 | 100万回 |

**PC中継をやめるだけでは Active CPU が足りない。** 項目8・9の削減とセットで初めて収まる。
Hobby は超過しても課金されず、警告のうえプロジェクトが止められることがあるため、余裕を持って移すこと。

### Supabase Free

| | 実測 | 無料枠 |
