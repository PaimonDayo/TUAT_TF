# Pure retention planning candidate

`retention.mjs` exports `planBackupRetention(input)`. It has no CLI, filesystem, environment, database or provider access and always returns `dryRun:true`. Nothing calls it from the backup supervisor. The receipt persistence, capacity probing, provider checks and deletion integration described below do **not** exist yet. No real archive or credential was used for its tests.

The caller supplies bounded flat JSON receipt metadata, explicit `identity` (`instanceId`, current `generation`, canonical UTC `startedAt`, `databaseSystemIdentifier`), `scope` (`targetFingerprint`, `storageScopeId`, `archiveKeyId`, each a 64-hex reviewed identity digest), the exact current `protectedPair`, a UUID `planNonce`, explicit millisecond `now`, `inventoryLimit` (1–4096) and `budgets`. Those digests must represent independently verified container/database, account/bucket and existing archive-key identities; self-asserted metadata does not prove a real target. Keep the existing namespace and archive key. Never put a key value in a receipt.

The proposed receipt contract is version 1 with `state:'verified'`, a UUID `receiptId`, the same instance/database/scope fields, its original lifecycle `generation`/`startedAt`, canonical UTC `capturedAt`/`verifiedAt`, exact `dumpKey`/`recoveryKey`, ciphertext SHA-256 values, nonempty `dumpEtag`/`recoveryEtag`, and `dumpBytes`/`recoveryBytes`. Keys must be the paired timestamp names under `ops/pc-backend/<instanceId>/backups/`. `localState` is `complete` or `absent`; `remoteState` is `verified` or `absent`. `localBytes`/`remoteBytes` must equal the ciphertext pair size when present and zero when known absent. Historical generations can support planning; only the exact supplied current-generation pair, present in both locations and verified less than 35 minutes ago, can be the protected pair. This does not replace the host's heartbeat/target/write guard.

Prepared, incomplete, uncertain, orphan, legacy and malformed records are held indefinitely and cannot become removal candidates. Optional known `localBytes`/`remoteBytes` on a held record are conservative usage reservations; missing sizes prevent a positive quota decision. Unknown extra/nested metadata and accessors are held without evaluating their payload and block all candidates because their object identities cannot be bound. A canonical future timestamp, conflicting verified scope, duplicate receipt/object identity (including a held attempt naming a verified object), changed/missing protected pair, excessive inventory or numeric overflow also blocks all candidates. A different legacy namespace remains held. It is never imported as a verified candidate merely because its filenames resemble new archives.

For verified pairs, the plan retains latest 24 local and latest 96 remote, plus the latest captured pair in each represented JST calendar day from today through the preceding 29 days. The current protected pair and latest two eligible pairs are always retained, including a protected pair captured before the other selected keepers but freshly verified. Fixed-count retention represents approximately 6/24 hours at ordinary 15-minute cadence; restarts can shorten that interval. It does not fabricate anchors for days without verified backups. Maximum selected verified sets are conservatively 55 local and 127 remote, plus all held objects.

`budgets` requires `maxLocalBytes`, `maxRemoteBytes`, `freeLocalBytes`, `minFreeLocalBytes`, `remoteBaselineBytes` (or explicit null when unknown), `nextPairBytes` (a conservative upper bound, at least 72), `maxRequestCount` and `maxTransferBytes`. Estimates include all supplied local/remote sizes, the independently established remote legacy baseline outside that inventory, and the next pair **before any candidate removal**. A successful existing upload/readback cycle uses six object requests and approximately twice the pair size in ciphertext transfer; database probes, future retention verification/deletes and other account activity are excluded. Those need separate bounded reservations before integration. Missing usage or exceeded limits sets `writeAllowed:false`; this is a metadata decision, not an account fee guarantee. Repeated uncertainty cannot coexist with bounded growth unless a future owner stops new archive creation/PUTs at the budget boundary. No uncertain pair should be purged to free capacity.

Output contains the identity/scope/nonce/time binding, digest of examined scalar inventory metadata, retained receipt references, exact paired removal candidates, held counts, quota estimates and a deterministic plan digest. Malformed payloads are represented by null in the inventory digest; their excluded content is not authenticated and no candidates are produced. A changed valid receipt, scope, nonce, budget or decision changes the plan digest. `planningAllowed`, `writeAllowed` and `removalCandidates` describe only this dry-run metadata calculation. They never authorize actual writes or deletion, never bypass host protection, and never establish actual quota or provider readiness. Unknown-size holds keep the quota decision unverified.

Future integration must persist an attempt before archive bytes or PUT, persist verified receipts only after both complete readbacks and the final target probe, serialize with the existing owner lock, preserve unknown outcomes, and recheck current ownership/target/fresh protection before any mutation. Before remote removal it must verify retained daily anchors, bind a fresh dry-run snapshot, recheck each exact object's ETag/size/hash, and prove provider conditional-delete behavior. A partial/unknown DELETE must stop the batch without automatic replay and preserve the local complete pair. Local removal also needs exact protected paths and regular-file/inode/hash checks; this planner has no path/deletion implementation.

Activation remains blocked on real target/account/key binding, prior writer/retention retirement, existing storage/capacity and request budgets, off-device recovery, and the new receipt/integration work. The existing old-backend worker still uses its own retention; this pure module does not replace or stop it.

Synthetic acceptance tests: `node --test ops/pc-backup/retention.test.mjs`. They exercise selection, JST boundaries, current/changed generation and scope, legacy/unknown preservation, inventory bounds, quota reservations, overflow and input immutability. They do not exercise real receipt creation, storage, deletion or provider semantics.
