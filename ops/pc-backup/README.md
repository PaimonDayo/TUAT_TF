# PC backup lifecycle candidate

This is an independent, default-disabled candidate. It does not start the old tunnel, mirror, endpoint publisher, task scheduler or remote retention. No production configuration or credentials were used to validate it. `node ops/pc-backup/run.mjs --check <absolute-plan.json>` (also the default mode) reads only the specified plan, without loading credentials, creating directories, probing a database or calling storage. The placeholder example intentionally cannot activate. `--execute` additionally requires `enabled:true`; normal operation is owned in-process by the PC host rather than a second task.

The host calls `startBackupSupervisor({configFile,expectedInstanceId,expectedDatabaseSystemIdentifier})`; both expected values must match `config.instanceId` and `config.target.databaseSystemIdentifier` before any lock, target read, backup or upload. `loadBackup(configFile)` returns `{config,env}` and validates existing private config/environment parents and files without modifying their ACL/modes. The dedicated environment accepts only `PC_BACKUP_ENCRYPTION_KEY`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`. Reuse the verified archive key and namespace; do not generate a replacement key or copy existing credentials into Git. Explicit Push recovery path is private and optional; a null path excludes it rather than discovering an old source.

Activation requires the owner to verify the existing PC app loopback data target's system ID, archive instance UUID, exact DB container ID/image/name, Compose project/service and data mount source, plus Windows WSL/Linux Docker binary hashes and absolute database command paths. The host's expected database ID must come from the established application data target, not merely from this plan's self-assertion. Docker explicitly uses the local `unix:///var/run/docker.sock`; WSL receives only required Windows OS context variables, never ambient provider/app credentials or `WSLENV`. Exact container metadata and `pg_control_system()` are rechecked before/after the dump, after upload and each 20 seconds. Changes or uncertainty immediately close readiness. No application rows are fetched by the identity probe. A cold restored DB or recreated container needs an explicit new target verification.

After the exclusive owner lock and protected startup status are written, the function returns `{identity:{instanceId,generation,startedAt},statusPath,stop}` while the first pair runs asynchronously. Reads/Auth may start immediately; writes remain closed until a fresh verified pair exists in this exact generation. A previous status is never loaded as evidence. The host injects `PC_APP_BACKUP_STATUS_PATH`, `PC_APP_BACKUP_INSTANCE_ID`, `PC_APP_BACKUP_GENERATION`, `PC_APP_BACKUP_STARTED_AT`, and its verified `PC_APP_BACKUP_DATABASE_SYSTEM_IDENTIFIER`; Jobs binds the same host identity. `status.mjs` and public `status-vectors.json` define the strict contract mirrored by Next: canonical UTC only, no future timestamps; heartbeat and target age strictly under 2 minutes; verified pair age strictly under 35 minutes; matching system ID, namespace, checksums and sizes. Heartbeat runs each 20 seconds; backups start at startup and then no more frequently than 15 minutes, with no overlapping pair operation.

Each backup uses actual custom-format `pg_dump` of public/auth/storage. Existing `TUATPC01` AES-256-GCM and paired recovery verification are reused. Recovery includes Vault secrets, cron metadata and only an explicitly configured Push environment. Encrypted bytes are written under an owner+SYSTEM protected state directory before upload; PUT is conditional on a new key, then HEAD and an exact-size, SHA-256 checked bounded GET readback verify both ciphertexts. The original dump/recovery authenticated-decryption check precedes upload. No plaintext/key is persisted or printed. Each provider request/readback is bounded; no uncertain pair is blindly resent or deleted. An ordinary upload failure or capacity-only refusal can retain the prior same-generation attestation until 35 minutes; incomplete inventory, identity/reverification, target/ownership/clock uncertainty fails immediately. Unverified local encrypted pairs remain for operator reconciliation. No local or remote deletion is implemented.

The supervisor persists a fresh `receipts/<receipt UUID>.json` prepared intent exclusively before dump/archive/PUT. It binds instance/generation/start/database, canonical capture time and both object keys to digests of the exact target, storage account/bucket and existing archive-key identity; credentials/key values are not stored. The initial intent reserves `capacity.maxPairBytes` in each location; actual sizes/hashes narrow that reservation before encrypted local writes. A missing listing entry cannot release an uncertain reservation, because a late PUT might still commit. After both local writes, both remote readbacks and a final target probe, matching nonempty HEAD/GET ETags and a verified receipt are persisted. A second complete inventory/readback and private dry-run manifest must succeed before readiness is published. The original verified timestamp and CAS PUT behavior are unchanged. Incomplete/unknown attempts remain prepared and held indefinitely; no replay, recovery takeover or deletion is added.

Enabled execution requires one explicit `capacity` block: `inventoryLimit` (1–4096), `maxLocalBytes`, `maxRemoteBytes`, `minFreeLocalBytes`, `maxPairBytes`, `maxRequestCount`, `maxTransferBytes`, all safe nonnegative integers. No operational values are inferred or written into existing configuration. A disabled prepare/mock plan can omit the block. Local accounting covers the **entire dedicated state directory**, including receipts, status, manifest, temp and legacy files; an unknown directory, redirect, changed file, deadline or excessive entry count rejects the inventory. `statfs` supplies available bytes on that volume. Remote accounting covers only the exact `ops/pc-backend/<instanceId>/backups/` prefix with complete, bounded pagination; images, other namespaces/buckets/accounts are outside this cap. These are neither a free-tier nor an account-cost guarantee.

At startup and each 15-minute backup cycle, same-scope verified local ciphertexts are hashed with a 64KiB buffer and remote pairs are reverified sequentially with matching list/HEAD/conditional-GET ETags, lengths, metadata and SHA-256. Large local archives are never loaded together. The 20-second heartbeat adds no listing or ciphertext GET. The first-pair capacity admission is separate from protected-pair retention selection. It counts all actual usage plus held reservations and the next pair and local metadata **before any possible removal**. Malformed/unknown-size receipts leave quota unverified; future timestamps, missing pairs, scope/key conflicts, incomplete pages or overflow reject activation. A full-cycle request/transfer allowance is checked before any ciphertext GET or dump/PUT. See [RETENTION-PLAN.md](RETENTION-PLAN.md) for exact bounds and dry-run scope. Growing held/legacy archives and daily keepers eventually block new backups at the explicit boundary; this candidate cannot reclaim space.

`stop()` marks maintenance/protected immediately, cancels active commands and body streams, schedules no further work, and drains for at most 10 seconds. Only a verified drained owner releases its exact lock. WSL parent timeout/abort cannot prove a Linux child exited: any command failure permanently prevents further commands in that generation and retains the lock on stop. There is no automatic stale-lock takeover or broad process kill. An operator must establish the exact owned command has ended and reconcile the old generation before removing its lock; this policy avoids overlapping a possibly continuing dump. A noncooperative adapter also retains the lock after bounded drain. Host shutdown first calls stop to protect immediately, drains gateway/Next, then awaits the bounded result; `drained:false` is an unresolved owner, never a successful stop. Optional `onFatal({reason})` notifies the owning host once on ownership, clock or status-publication failure so it immediately stops new gateway dispatch and owned Next. Ordinary target/upload failures publish protection or retain a qualifying pair without this shutdown callback. If a status write itself is impossible, readers only see its old record expire within 2 minutes; owner shutdown supplies the immediate boundary.

Synthetic tests cover startup freshness, interval/no overlap, exact target mismatch, upload ambiguity and freshness expiry, ownership loss, clock rollback, real exclusive private locks, read-only loading, full inventory/capacity refusal, held reservations and stalled stream cancellation. They use generated test identities/key, fake transports and private synthetic files only; provider requests are zero. Production target/account/key binding, actual quotas/fees and old writer/retention shutdown remain activation gates. The earlier `ops/pc-host/backup-review` proof covers actual synthetic full-app dump/encrypted-pair/fresh restore. Neither proves off-device retrieval, separate recovery key custody, OS configuration, cloud Auth trust, host environments, Jobs journal or R2 image bytes. Cold restore must separately reapply the reviewed nonsecret authenticator pre-request setting and matching public schema prerequisite documented there; the two-file archive does not capture those cluster/bootstrap settings.
