# PC backup lifecycle candidate

This is an independent, default-disabled candidate. It does not start the old tunnel, mirror, endpoint publisher, task scheduler or remote retention. No production configuration or credentials were used to validate it. `node ops/pc-backup/run.mjs --check <absolute-plan.json>` (also the default mode) reads only the specified plan, without loading credentials, creating directories, probing a database or calling storage. The placeholder example intentionally cannot activate. `--execute` additionally requires `enabled:true`; normal operation is owned in-process by the PC host rather than a second task.

The host calls `startBackupSupervisor({configFile,expectedInstanceId,expectedDatabaseSystemIdentifier})`; both expected values must match `config.instanceId` and `config.target.databaseSystemIdentifier` before any lock, target read, backup or upload. `loadBackup(configFile)` returns `{config,env}` and validates existing private config/environment parents and files without modifying their ACL/modes. The dedicated environment accepts only `PC_BACKUP_ENCRYPTION_KEY`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`. Reuse the verified archive key and namespace; do not generate a replacement key or copy existing credentials into Git. Explicit Push recovery path is private and optional; a null path excludes it rather than discovering an old source.

Activation requires the owner to verify the existing PC app loopback data target's system ID, archive instance UUID, exact DB container ID/image/name, Compose project/service and data mount source, plus Windows WSL/Linux Docker binary hashes and absolute database command paths. The host's expected database ID must come from the established application data target, not merely from this plan's self-assertion. Docker explicitly uses the local `unix:///var/run/docker.sock`; WSL receives only required Windows OS context variables, never ambient provider/app credentials or `WSLENV`. Exact container metadata and `pg_control_system()` are rechecked before/after the dump, after upload and each 20 seconds. Changes or uncertainty immediately close readiness. No application rows are fetched by the identity probe. A cold restored DB or recreated container needs an explicit new target verification.

After the exclusive owner lock and protected startup status are written, the function returns `{identity:{instanceId,generation,startedAt},statusPath,stop}` while the first pair runs asynchronously. Reads/Auth may start immediately; writes remain closed until a fresh verified pair exists in this exact generation. A previous status is never loaded as evidence. The host injects `PC_APP_BACKUP_STATUS_PATH`, `PC_APP_BACKUP_INSTANCE_ID`, `PC_APP_BACKUP_GENERATION`, `PC_APP_BACKUP_STARTED_AT`, and its verified `PC_APP_BACKUP_DATABASE_SYSTEM_IDENTIFIER`; Jobs binds the same host identity. `status.mjs` and public `status-vectors.json` define the strict contract mirrored by Next: canonical UTC only, no future timestamps; heartbeat and target age strictly under 2 minutes; verified pair age strictly under 35 minutes; matching system ID, namespace, checksums and sizes. Heartbeat runs each 20 seconds; backups start at startup and then no more frequently than 15 minutes, with no overlapping pair operation.

Each backup uses actual custom-format `pg_dump` of public/auth/storage. Existing `TUATPC01` AES-256-GCM and paired recovery verification are reused. Recovery includes Vault secrets, cron metadata and only an explicitly configured Push environment. Encrypted bytes are written under an owner+SYSTEM protected state directory before upload; PUT is conditional on a new key, then HEAD and an exact-size, SHA-256 checked bounded GET readback verify both ciphertexts. The original dump/recovery authenticated-decryption check precedes upload. No plaintext/key is persisted or printed. Each provider request/readback is bounded; no uncertain pair is blindly resent or deleted. An ordinary upload failure can retain the prior same-generation attestation until 35 minutes; target/ownership/clock uncertainty fails immediately. Unverified local encrypted pairs remain for operator reconciliation. This first candidate does not prune local archives or manage remote retention; capacity/retention ownership remains an activation gate.

The supervisor persists a fresh `receipts/<receipt UUID>.json` prepared intent exclusively before dump/archive/PUT. It binds instance/generation/start/database, canonical capture time and both object keys to digests of the exact target, storage account/bucket and existing archive-key identity; credentials/key values are not stored. Pair sizes/hashes are persisted before encrypted local writes, conservatively reserving the full pair in both locations even if only one file or object is saved. After both local writes, both remote readbacks and a final target probe, matching nonempty HEAD/GET ETags and a verified receipt are persisted before readiness is published. This is an at-capture proof, not a perpetual inventory assertion. Incomplete/unknown attempts remain prepared and are held indefinitely; no replay, recovery takeover or deletion is added. A failure to persist the final receipt cannot publish a new attestation. Current receipt metadata fits the pure retention planner, but actual protected inventory discovery/reverification, capacity/request reservation, planner integration and removal remain unimplemented activation gates. The planner is still dry-run only.

`stop()` marks maintenance/protected immediately, cancels active commands and body streams, schedules no further work, and drains for at most 10 seconds. Only a verified drained owner releases its exact lock. WSL parent timeout/abort cannot prove a Linux child exited: any command failure permanently prevents further commands in that generation and retains the lock on stop. There is no automatic stale-lock takeover or broad process kill. An operator must establish the exact owned command has ended and reconcile the old generation before removing its lock; this policy avoids overlapping a possibly continuing dump. A noncooperative adapter also retains the lock after bounded drain. Host shutdown first calls stop to protect immediately, drains gateway/Next, then awaits the bounded result; `drained:false` is an unresolved owner, never a successful stop. Optional `onFatal({reason})` notifies the owning host once on ownership, clock or status-publication failure so it immediately stops new gateway dispatch and owned Next. Ordinary target/upload failures publish protection or retain a qualifying pair without this shutdown callback. If a status write itself is impossible, readers only see its old record expire within 2 minutes; owner shutdown supplies the immediate boundary.

Synthetic tests cover startup freshness, interval/no overlap, exact target mismatch, upload ambiguity and freshness expiry, ownership loss, clock rollback, real exclusive private locks, read-only loading and stalled stream cancellation. They use generated test identities/key and fake transports only. The earlier `ops/pc-host/backup-review` proof covers actual synthetic full-app dump/encrypted-pair/fresh restore. Neither proves the production backup target/account, off-device retrieval, separate recovery key custody, OS configuration, cloud Auth trust, host environments, Jobs journal or R2 image bytes. Cold restore must separately reapply the reviewed nonsecret authenticator pre-request setting and matching public schema prerequisite documented there; the two-file archive does not capture those cluster/bootstrap settings.
